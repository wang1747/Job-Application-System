# 简历生成模块「结构化生成」改造方案

> 目标：把「一次性生成纯文本」升级为「生成结构化数据 + 渲染成纯文本」，为后续模板、分段编辑、评分等能力铺路。
> 原则：改动最小、复用已有能力（一页校验 / ats_checker / 导出排版）、向后兼容（现有简历列表和导出不受影响）。

---

## 一、核心设计决策

**「结构化数据」是主数据，「纯文本」只是渲染产物。**

当前 `resume_text` 是一整段纯文本，导致后续无法定位「哪段是项目经历」、无法逐段编辑、无法套模板。

改造后：
1. LLM 输出**结构化 JSON**（每个 section 独立字段）
2. 后端把结构化 JSON **渲染成纯文本**（用于存库、列表展示、复用现有 PDF/Word 导出）
3. 前端按**结构化字段**渲染结果，而不是 `<pre>` 纯文本

这样现有的 `export_service.py`（PDF/Word 排版）和 `list_resumes`（列表分组）**完全不用改**，因为它们本来就消费纯文本。

---

## 二、结构化 JSON Schema（LLM 输出契约）

让 LLM 严格输出下面的 JSON（这是前后端的「合同」，也是本方案的核心）：

```json
{
  "name": "王照涵",
  "position": "Python 后端实习",
  "contact": {
    "phone": "13800138000",
    "email": "wang@qq.com",
    "github": "https://github.com/wang1747"
  },
  "summary": "2~3 句个人总结，突出与目标 JD 匹配的优势",
  "education": [
    {
      "school": "河北环境工程学院",
      "major": "数据科学与大数据技术",
      "degree": "本科",
      "start": "2023-09",
      "end": "2027-06",
      "detail": "主修课程 / 绩点 / 荣誉（可空）"
    }
  ],
  "experiences": [
    {
      "type": "project",
      "name": "OfferFlow 求职系统",
      "role": "后端开发",
      "start": "2026-03",
      "end": "2026-08",
      "bullets": [
        "用 FastAPI + LangChain 搭建多智能体编排，支撑日均 1000 次调用",
        "将接口响应时间从 800ms 降到 100ms"
      ]
    }
  ],
  "skills": ["Python", "FastAPI", "Docker"],
  "certifications": ["软考中级（可空数组）"],
  "tips": ["建议补充量化成果"]
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| name | string | ✅ | 姓名 |
| position | string | ✅ | 求职意向/目标岗位 |
| contact | object | 建议 | phone / email / github，可缺 |
| summary | string | 可选 | 个人总结，2~3 句 |
| education | array | ✅（或 experience 至少其一） | 教育经历，通常 1~2 条 |
| experiences | array | ✅（或 education 至少其一） | 项目+实习+工作合并，`type` 区分 project/internship/work |
| skills | array | 建议 | 技能列表 |
| certifications | array | 可选 | 证书 |
| tips | array | 可选 | AI 建议（保留现有能力） |

**约束（写进 prompt）**：
- 只能使用用户填的信息，禁止编造学校/公司/时间/数字/证书/技能
- `experiences[].bullets` 每条「动词开头 + 方法 + 量化成果」，2~3 条
- 整体控制在一页以内

## 三、纯文本渲染规则（结构化 → resume_text）

渲染出的纯文本必须能被现有 `structure.py` 的 `parse_resume_structure` 正确识别（第一行姓名、分节标题），否则导出会乱。

渲染模板（严格遵守，分节标题用 `structure.py` 已识别的词）：

```
{name}
{phone} | {email} | {github}

求职意向
{position}

个人总结
{summary}

教育经历
{school} {major} {degree} {start} ~ {end}
{detail}

{type 对应的分节标题，见下}
{name}（{role}，{start} ~ {end}）
- {bullets[0]}
- {bullets[1]}

技能
{skill1}、{skill2}、{skill3}

证书（certifications 非空才渲染这一节）
{cert1}、{cert2}
```

要点：
1. `type` → 分节标题映射：`project`→「项目经历」、`internship`→「实习经历」、`work`→「工作经历」。同 type 合并到同一节下，不同 type 各成一节。
2. `summary` 为空则跳过「个人总结」节；`certifications` 为空则跳过「证书」节。
3. 建议这个渲染逻辑单独放一个函数（如 `render_resume_text(structured) -> str`），前端预览和存库共用同一份，避免两处逻辑不一致。

## 四、后端改动清单

目录：`backend/app/modules/resume_generation/`

| 文件 | 改动 |
|---|---|
| `contracts.py` | `GenerationResult` 改为承载结构化字段（name/position/contact/summary/education/experiences/skills/certifications/tips/error），去掉纯文本 `resume_text` 字段；渲染交给单独函数 |
| `prompts.py` | `SYSTEM_PROMPT` 改为要求输出上面第二节的 JSON，加「事实保真 + 一页 + bullets 要点化」约束 |
| `services.py` | ① 解析结构化 JSON → 校验关键字段非空 → ② 调渲染函数得到 `resume_text` → ③ 一页校验（见第五节）→ ④ 返回结构化 + 渲染文本 |
| `routes.py` | 保存时 `raw_text = resume_text`（渲染文本，保证导出/列表兼容）；把结构化数据塞进 `parsed_json`（供前端逐段渲染/编辑） |
| `schemas.py` | **不改**（输入表单不变） |
| 新增 | 建议新建 `render.py`（或放 services.py 内），承载「结构化 → 纯文本」渲染函数 |

**关键点**：`parsed_json` 里存结构化数据时，别覆盖 `upload_resume` 生成的 `{sections, skills, has_contact}` 摘要，可以并存（加一个 `structured` 键），例如：
```python
parsed_json = {**摘要, "structured": {结构化字段}, "kind": "generated"}
```
这样后续前端能拿到结构化，同时老逻辑（skills 提取、列表分组）不受影响。

## 五、一页硬校验（复用，别重写）

复用 `app/modules/resume/optimizer/service.py` 里现成的：

- `_estimate_too_long(original, optimized)` —— 判断是否超一页
- `_condense_to_one_page(text, user)` —— 三刀裁剪法精简

在 `services.py` 生成流程里加一步：
1. 渲染得到 `resume_text`
2. 若 `_estimate_too_long("", resume_text)` 为真（生成场景没有「原文」，用绝对长度判断即可，即超过 1400 字符），调 `_condense_to_one_page` 精简
3. 精简后再渲染/或直接用精简文本

> 注意：`_estimate_too_long` 第一个参数是「原文」，生成场景可传空串，让它走「绝对长度」分支。

## 六、前端改动清单

目录：`frontend/src/`

| 文件 | 改动 |
|---|---|
| `types/index.ts` | `ResumeGenerationResult` 增加结构化字段（name/contact/summary/education/experiences/skills/certifications），保留 `resume_text` 与 `sections`/`tips` 作兼容 |
| `pages/ResumeGenerate.tsx` | 结果区由 `<pre>{resume_text}</pre>` 改为按结构化字段渲染：姓名+联系方式头部、求职意向、个人总结、教育、逐段 experiences（每条 name/role/时间 + bullets 列表）、技能、证书、tips |

**前端渲染顺序建议**（主次分明）：
1. 姓名（大字）+ 联系方式
2. 求职意向
3. 个人总结
4. 教育经历
5. 项目/实习/工作经历（逐条，bullet 列表）
6. 技能（标签化）
7. 证书
8. tips（保留，amber 徽标）

## 七、兼容性保障（务必验证）

改造完成后要确认这些老功能不破：

1. **导出 PDF/Word**：`export_to_pdf/word` 消费 `raw_text`（渲染文本）→ 应正常（渲染规则已兼容 `parse_resume_structure`）
2. **简历列表**：`list_resumes` 按 `target_jd`/原版分组 → 生成的简历 `kind=generated`（非 optimized），会作为「基础简历」出现，正常
3. **简历优化模块**：生成的简历可作为「基础简历」被优化模块选中再优化 → 正常
4. **列表 label**：生成的简历 `source_file="ai_generated"` → 前端 `SOURCE_LABELS` 已映射为「AI 生成」

## 八、分阶段实施建议

| 阶段 | 内容 | 价值 |
|---|---|---|
| **阶段 1（本次）** | 结构化输出 + 渲染兼容 + 一页校验 | 打地基，其余高级功能的前提 |
| 阶段 2 | 前端按结构化渲染 + 逐段「重新生成」按钮 | 体验提升，可微调 |
| 阶段 3 | 复用 ats_checker 给结构化评分 + 结构化 JD 匹配（must_have/nice_to_have） | 对标 Rezi Score / Keyword Targeting |

**建议先只做阶段 1**，把「结构化 JSON + 渲染 + 一页校验」跑通，再叠加阶段 2、3。
